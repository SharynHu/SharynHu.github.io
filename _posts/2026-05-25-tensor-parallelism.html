The Problem It Solves

A large model's weight matrices do not fit in one GPU's HBM. Even if they did, a single GPU's compute might become the throughput bottleneck. Tensor parallelism splits individual weight matrices across multiple GPUs so the matrix multiplications can be computed in parallel.

The attention score computation itself, softmax(QKᵀ/√d) @ V, is not split by tensor parallelism. It runs fully and locally on each GPU for that GPU's assigned heads.

Assume 4-way tensor parallelism, TP=4, throughout this page. The forward pass alternates between two states:

  • Replicated state: every GPU holds identical x: [batch, seq_len, d_model]. Cheap local operations such as RMSNorm and residual add run with no communication.
  • Sharded state: each GPU holds a different slice of an intermediate. Expensive matmuls run in parallel, then an AllReduce returns the output to replicated state.

Terminology

To be precise throughout this page:

  • Transformer layer — the full repeating unit stacked N times. Contains two sublayers.
  • Attention sublayer — first half of a transformer layer: RMSNorm + attention mechanism + residual add.
  • Attention mechanism — Q/K/V projections + score computation + output projection. No norm, no residual.
  • FFN sublayer — second half of a transformer layer: RMSNorm + SwiGLU FFN + residual add.
  • SwiGLU FFN — the three weight matrices plus activation. No norm, no residual.

Attention Sublayer: Step by Step

The attention sublayer contains: RMSNorm → attention mechanism → residual add.

Modern transformers use GQA (Grouped Query Attention):

  • num_heads query heads
  • num_kv_heads key/value heads, where num_kv_heads < num_heads

For example, Qwen2.5-7B uses num_heads=28 and num_kv_heads=4.

👉

GQA constraint under TP

Many implementations require TP to divide the attention-head and KV-head layout cleanly.

  • If TP ≤ num_kv_heads and num_kv_heads % TP == 0, each rank can get num_kv_heads / TP distinct KV heads.
  • If TP > num_kv_heads, KV heads may need replication or special grouping, depending on the backend. Some systems restrict these TP choices instead of supporting every layout.

With TP=4, heads are divided across GPUs:

  • GPU 0: Q heads 0-6, KV head 0
  • GPU 1: Q heads 7-13, KV head 1
  • GPU 2: Q heads 14-20, KV head 2
  • GPU 3: Q heads 21-27, KV head 3

RMSNorm (pre-attention)

RMSNorm is replicated on all GPUs.

Each RMSNorm instance computes:

\[ \mathrm{RMS}(x)=\sqrt{\frac{1}{d}\sum_{i=1}^{d} x_i^2 + \epsilon} \]
\[ \mathrm{RMSNorm}(x)=\gamma \odot \frac{x}{\mathrm{RMS}(x)} \]
  • RMSNorm requires the full d_model vector to compute the RMS, because it reduces across all d_model elements.
  • RMSNorm is not tensor-parallelized.
  • All GPUs run it simultaneously and independently, producing identical results. No GPU waits.
  • Each RMSNorm instance has its own independent γ: [d_model], replicated on every GPU.

After the previous layer's AllReduce, except for layer 0, the input matrix x is complete and identical on all GPUs:

  • GPU 0: x: [batch, seq_len, d_model] ← complete, identical copy
  • GPU 1: x: [batch, seq_len, d_model] ← complete, identical copy
  • GPU 2: x: [batch, seq_len, d_model] ← complete, identical copy
  • GPU 3: x: [batch, seq_len, d_model] ← complete, identical copy

All four GPUs run RMSNorm(x) locally and simultaneously. They get the same result, with no communication.

Q, K, V Projections (column-wise split)

Recall the QKV projection for Grouped Query Attention:

\[ W_Q \in \mathbb{R}^{d_{model} \times \text{num\_q\_heads}\times d_{head}}, \quad W_K \in \mathbb{R}^{d_{model} \times \text{num\_kv\_heads}\times d_{head}}, \quad W_V \in \mathbb{R}^{d_{model} \times \text{num\_kv\_heads}\times d_{head}} \]
\[ Q = XW_Q,\quad K = XW_K,\quad V = XW_V \]

Considering one input vector x, we multiply it with each column of the weight matrix W_Q:

\[ q_j = x \cdot W_Q[:,j] \]

Each column of a projection matrix produces one independent output feature: a scalar that is a learned linear combination of all d_model input elements.

Since output features are independent, the weight matrix can be split column-wise across GPUs without changing correctness. Each GPU computes its own subset of output features.

Weight shards per GPU:

  • Q_proj: [d_model, num_q_heads/4 * d_head]
  • K_proj: [d_model, num_kv_heads/4 * d_head]
  • V_proj: [d_model, num_kv_heads/4 * d_head]

After the projection, each GPU holds its own portion of QKV, split by heads:

  • Q_i = X @ Q_proj_shard_i → [batch, seq_len, (num_q_heads/4) * d_head]
  • K_i = X @ K_proj_shard_i → [batch, seq_len, (num_kv_heads/4) * d_head]
  • V_i = X @ V_proj_shard_i → [batch, seq_len, (num_kv_heads/4) * d_head]

We are now in the sharded state. No communication happens here: each GPU works independently on the same X.

Attention Score Computation (fully local)

Each GPU runs the complete attention math for its own heads. The attention score computation is not tensor-parallelized. It is local to each GPU because heads are independent of one another.

GPU i reshapes:

  • Q_i: [batch, num_q_heads/4, seq_len, d_head]
  • K_i: [batch, num_kv_heads/4, seq_len, d_head]
  • V_i: [batch, num_kv_heads/4, seq_len, d_head]

GPU i computes:

  • scores_i = softmax(Q_i @ K_i.T / sqrt(d_head)) → [batch, num_q_heads/4, seq, seq]
  • attn_out_i = scores_i @ V_i → [batch, num_q_heads/4, seq, d_head]

No communication. GPU i has everything it needs.

Output Projection (row-wise split)

Without tensor parallelism, the outputs of all heads would be concatenated first, then multiplied by W_o.

Under TP, each GPU holds a partial concatenation, meaning its own heads' outputs, and the corresponding row shard of W_o. Each GPU produces a partial sum across the full d_model output dimension. That partial sum is incomplete on its own, so it must be summed across GPUs.

  • GPU i holds attn_out_i reshaped as [batch, seq_len, (num_q_heads/4) * d_head]
  • GPU i holds row shard W_o_shard_i: [(num_heads/4) * d_head, d_model]

GPU i computes:

  • partial_i = attn_out_i @ W_o_shard_i → [batch, seq_len, d_model]

Although partial_i has the same shape as the final output, each element is generated only from attn_out_i, which has one quarter of attn_out. The next step is an AllReduce to recover the full output.

AllReduce #1 + Residual Add

  • Y_attn = AllReduce(partial_0 + partial_1 + partial_2 + partial_3)
    → [batch, seq_len, d_model], full result replicated on all GPUs.
  • x_residual = x_residual + Y_attn → [batch, seq_len, d_model], replicated.

We return to the replicated state. The attention sublayer is complete.

⚠️

Bias handling under row-parallel projection

If the row-parallel projection, such as W_o here or W_down later, has a bias term, the bias must be added after the AllReduce on one rank only, then replicated. Adding the bias locally to partial_i before the AllReduce would sum it TP times.

Llama and Qwen2.5 both use bias-free W_o and W_down, so this is latent in most current deployments. Qwen2.5 does use bias on Q/K/V, which are column-parallel; that bias is sharded with its matrix and added locally, so no correction is needed there.

FFN Sublayer: Step by Step

The FFN sublayer contains: RMSNorm → SwiGLU FFN → residual add.

Modern LLMs such as Llama, Qwen, and Mistral use SwiGLU instead of a plain FFN. SwiGLU has three weight matrices:

  • W_gate: [d_model, d_ffn] ← gating branch
  • W_up: [d_model, d_ffn] ← value branch
  • W_down: [d_ffn, d_model] ← projects back to d_model
  • output = (SiLU(X @ W_gate) * (X @ W_up)) @ W_down

The element-wise multiply between the gate branch and the up branch is the gated activation. A standard FFN does activation(X @ W1) @ W2. SwiGLU adds a learned gate that filters the value branch.

RMSNorm (pre-FFN)

This is the same as the RMSNorm before attention.

  • x_residual: [batch, seq_len, d_model] ← from the attention sublayer residual add, replicated.
  • All GPUs compute locally and simultaneously: X = RMSNorm(x_residual) → [batch, seq_len, d_model], replicated.

This is the replicated state. No communication is needed.

Gate and Up Projections (column-wise split)

Same logic as Q/K/V: output features of W_gate and W_up are independent, so the column dimension can be sharded. Crucially, GPU i's gate shard and up shard cover the same slice of d_ffn, so their element-wise multiply is local and correct.

GPU i holds one quarter of W_gate and W_up, sharded by column:

  • W_gate_shard_i: [d_model, d_ffn/4]
  • W_up_shard_i: [d_model, d_ffn/4]

GPU i computes:

  • gate_i = SiLU(X @ W_gate_shard_i) → [batch, seq_len, d_ffn/4]
  • up_i = X @ W_up_shard_i → [batch, seq_len, d_ffn/4]
  • hidden_i = gate_i * up_i → [batch, seq_len, d_ffn/4], element-wise and local.

No communication. Both gate and up cover the same d_ffn slice, so the multiply needs no data from other GPUs.

Down Projection (row-wise split)

hidden_i has shape [batch, seq_len, d_ffn/4]. W_down maps d_ffn → d_model. Each GPU holds the corresponding row shard.

GPU i holds one quarter of W_down, sharded by row:

  • W_down_shard_i: [d_ffn/4, d_model]

GPU i computes:

  • partial_i = hidden_i @ W_down_shard_i → [batch, seq, d_model], a partial sum.

AllReduce #2 + Residual Add

  • Y_ffn = AllReduce(partial_0 + partial_1 + partial_2 + partial_3)
    → [batch, seq_len, d_model], full result replicated on all GPUs.
  • x_residual = x_residual + Y_ffn → [batch, seq_len, d_model], replicated.

We are back in the replicated state, ready for the next transformer layer.

Per transformer layer: 2 AllReduces total.

For a 32-layer model: 32 × 2 = 64 AllReduces per forward pass.

KV Cache Under Tensor Parallelism

Each GPU Stores Only Its Own KV Heads

Since K and V projections are column-wise sharded, each GPU only computes K and V for its local KV heads. The KV cache is naturally partitioned:

  • GPU 0 KV cache: K, V for KV head 0 → shape per token: [2, n_layers, 1, d_head]
  • GPU 1 KV cache: K, V for KV head 1 → shape per token: [2, n_layers, 1, d_head]
  • GPU 2 KV cache: K, V for KV head 2 → shape per token: [2, n_layers, 1, d_head]
  • GPU 3 KV cache: K, V for KV head 3 → shape per token: [2, n_layers, 1, d_head]

No shared KV cache. Each GPU manages its own paged block pool in its own HBM independently.

Block Tables Are Per-GPU

The CPU scheduler manages logical block IDs. The same logical block ID maps to different physical HBM addresses on each GPU, but all store the same token positions and different heads' KV data:

  • CPU assigns logical block IDs [4, 7, 12] for a request.
  • GPU 0: block_table[4] → GPU 0 HBM base + 4 * page_size (KV head 0 data)
  • GPU 1: block_table[4] → GPU 1 HBM base + 4 * page_size (KV head 1 data)
  • GPU 2: block_table[4] → GPU 2 HBM base + 4 * page_size (KV head 2 data)
  • GPU 3: block_table[4] → GPU 3 HBM base + 4 * page_size (KV head 3 data)

At the request level, the scheduler can usually operate on logical block IDs instead of individual TP shards. From this perspective:

  • It manages logical block IDs as usual.
  • It assigns block tables per request.
  • It sends the same logical block table to all TP ranks.
  • It reads back a single set of output token IDs after the forward pass.

But this does not mean the serving engine has no TP awareness. The engine still knows TP size, per-rank KV capacity, distributed executor layout, and model-shard placement. TP details are mostly hidden from request-level scheduling, but they still affect initialization, memory capacity, and physical block allocation.

A cleaner decomposition is:

  • request scheduler ← mostly works with requests and logical KV blocks
  • distributed GPU executor ← TP-aware, maps logical blocks to per-rank physical KV pages and runs the sharded model

The boundary is close to: logical block tables in, token IDs out. TP is mostly contained inside the GPU execution layer, but capacity planning and worker initialization still depend on it.

Decode: No KV Communication Needed

During decode, each GPU reads its local KV pages. The attention-score computation is fully local: GPU i uses only its own K_i and V_i from its own HBM.

The head-based split that enables parallel attention is the same split that partitions the KV cache. They are the same slices of the same data.

Memory Implication

With TP=4 in this Qwen2.5-7B example, each GPU stores one quarter of the total KV cache because the 4 KV heads are evenly sharded across the 4 TP ranks. KV cache is often the dominant consumer of HBM at large batch sizes, so this head split can distribute the KV-memory cost.

This 1/TP KV-memory reduction is conditional: it assumes KV heads are evenly sharded across TP ranks. If KV heads are replicated, or if the backend uses a different GQA/MQA layout, the KV-memory saving can be smaller or absent.

Prefix Caching With TP

The CPU radix tree stores logical block IDs as usual. On a cache hit, the block table is passed to all GPUs simultaneously. Each GPU independently reads its local KV pages, so no cross-GPU coordination is needed.

Input Embedding and LM Head Under TP

The transformer block is where most of the TP action happens, but the model has two boundary layers that are also sharded with a different pattern: vocabulary parallelism.

Input Embedding (vocabulary-parallel)

The embedding table E ∈ R^{V × d_model} maps token IDs to dense vectors, where V is the vocabulary size. Under TP, the vocabulary dimension is sharded across GPUs:

  • GPU i holds E_shard_i: [V/TP, d_model], the rows for token IDs in its assigned vocab range.

Each GPU performs a masked lookup: if a token ID falls in its vocab range, it fetches the embedding; otherwise it produces zeros. An AllReduce across TP ranks combines the per-rank results into the full embedding tensor, replicated on all GPUs and ready for layer 0.

In effect, the input embedding adds one more AllReduce to the forward pass, before the first transformer layer.

LM Head (vocabulary-parallel)

The LM head is the transpose pattern of the embedding:

  • W_LM ∈ R^{d_model × V} maps the final hidden state to vocabulary logits.
  • Some models tie LM head weights to the input embedding. Qwen2.5-1.5B does; Llama-3 70B does not.
  • Either way, the LM head is sharded along the vocabulary dimension.
  • GPU i holds W_LM_shard_i: [d_model, V/TP].
  • GPU i computes logits_i = hidden @ W_LM_shard_i → [batch, seq_len, V/TP].

The final step depends on how sampling is implemented. For greedy or top-k sampling, an AllGather along the vocab dimension may assemble the full [batch, seq_len, V] logits on all ranks, then sampling happens locally. Some implementations instead do argmax or sample locally per shard, then AllReduce the local winner with its score. This avoids shipping the full vocab tensor but is trickier for top-k/top-p.

The LM head is often the single largest matmul in the forward pass. For small-hidden-size models like Qwen2.5-1.5B, V · d_model can rival a full FFN layer. That is why vocabulary parallelism matters for throughput: it distributes both compute and memory.

Why NVLink Matters

Tensor parallelism strongly prefers very fast inter-GPU communication because AllReduces happen inside every layer. The GPUs are tightly coupled. PCIe can work for smaller models or lower-throughput deployments, but for large-model TP it often makes communication the bottleneck. NVLink on H100 gives roughly 900 GB/s bidirectional bandwidth, which is what makes tight tensor parallelism practical.

This is why tensor parallelism is typically kept within a single NVLink / NVSwitch domain, while pipeline parallelism can be used across nodes where only InfiniBand is available.

Sequence Parallelism and Context Parallelism

Plain tensor parallelism shards model dimensions, not the sequence dimension. A pure TP implementation still has replicated-state regions, such as RMSNorm and residual add, where every TP rank may hold the full [batch, seq_len, d_model] activation.

In training frameworks, Sequence Parallelism (SP) is often paired with TP to reduce this replicated activation memory. SP shards some activation states along the sequence dimension:

  • In RMSNorm / residual regions: each rank can hold [batch, seq_len / TP, d_model], its own sequence slice.
  • Around TP-sharded matmul regions: collectives move between sequence-sharded and tensor-sharded layouts.

A common implementation decomposes an AllReduce-like transition into:

  • AllGather along the sequence dimension when full activations are needed.
  • ReduceScatter when summed outputs can be returned to sequence-sharded form.

Total communication volume may be similar to an AllReduce, but the decomposition exposes better opportunities for memory saving and compute/communication overlap.

For serving and inference, do not assume this training-style SP is automatically enabled. Serving systems may use plain TP, TP plus specialized communication overlap, or separate context parallelism for long-context attention. Context parallelism also uses the sequence dimension, but its goal is usually to split long-context attention/KV work across GPUs rather than to reduce training activation memory.

The clean separation is:

  • Tensor Parallelism (TP): shards model dimensions such as heads, hidden dimensions, FFN dimensions, vocab, and KV heads.
  • Sequence Parallelism (SP): training-oriented activation sharding along the sequence dimension.
  • Context Parallelism (CP): serving/long-context-oriented sequence sharding for attention/KV work.

This section is a natural extension of TP, but it is not part of the basic TP mechanism described above.
