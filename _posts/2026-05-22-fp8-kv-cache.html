The idea is simple: instead of storing KV cache tensors in FP16/BF16 (2 bytes per value), you quantize them down to FP8 (1 byte per value), roughly cutting the raw KV cache memory in half.

A useful rule of thumb:

\[ \begin{aligned} \text{KV cache size} \approx {} & 2 \times \text{num layers} \times \text{batch size} \times \text{sequence length} \\ & \times \text{KV heads} \times \text{head dimension} \times \text{bytes per element} \end{aligned} \]
  • FP16/BF16 uses 2 bytes per value.
  • FP8 uses 1 byte per value, so the same memory budget can hold roughly 2× as many KV values before scale/metadata overhead.

Floating Point Representation

A floating point number is represented in binary using 3 fields:

In binary floating point:

  • sign → positive or negative
  • exponent → the internal power-of-two scale inside the floating-point value
  • mantissa → the actual digits (the precision)

How to get the FP number from its representation

For normalized finite values, the simplified formula is:

\[ \text{value} = (-1)^{\text{sign}} \times 2^{(\text{exponent} - \text{bias})} \times 1.\text{mantissa} \]

This formula does not cover zero, subnormal values, infinities, or NaNs. Those are handled by special exponent patterns.

Let's decode this FP32 bit pattern: 0 | 10000001 | 10100000000000000000000

  • Sign: (-1)^0 = +1 → positive
  • Exponent
    • 10000001 in binary = 129 in decimal
    • bias for FP32 = 127
    • exponent = 2(129-127) = 4
  • Mantissa:
    The stored bits are 10100000000000000000000. You read them as binary fraction digits after an implied 1.:
1.10100000000000000000000
  ↑↑
  bit1 = 1 → contributes 1 × 2^(-1) = 0.5
  bit2 = 0 → contributes 0 × 2^(-2) = 0
  bit3 = 1 → contributes 1 × 2^(-3) = 0.125
  rest are 0

1 + 0.5 + 0 + 0.125 = 1.625
  • Multiply everything: (+1) × 4 × 1.625 = 6.5 ✓

How to represent a number in FP32

To represent the number -6.5:

  • sign: negative → sign bit = 1
  • write 6.5 in binary: 6.5 = 110.1 in binary
  • normalize it (like scientific notation, shift until one digit before the decimal): 110.1 → 1.101 × 2^2
  • store the exponent
    FP32 uses a bias of 127, so you store 2 + 127 = 129 = 10000001 in the exponent field. The bias exists so you can represent negative exponents without a separate sign bit for the exponent.
  • store the mantissa:
    The leading 1. is always implied for normalized values, so you only store what comes after the dot: 101 followed by zeros to fill 23 bits: 10100000000000000000000
  • Final stored bits: 1|10000001|10100000000000000000000

What FP8 actually is

Before talking about FP8, make the convention explicit.

In this note, E4M3 and E5M2 first mean the bit allocation:

  • E4M3 — 1 sign bit, 4 exponent bits, 3 mantissa bits
  • E5M2 — 1 sign bit, 5 exponent bits, 2 mantissa bits

That bit allocation alone is not the whole FP8 dtype definition. Once the bit widths are fixed, the exact set of representable FP8 numbers still depends on:

  • exponent bias: shifts the exponent window and changes max/min range
  • reserved special patterns: whether top exponent/mantissa codes mean finite numbers, NaN, or infinity
  • zero/subnormal rules: whether negative zero exists, and how tiny values near zero are encoded
  • rounding and overflow policy: how real values are converted into FP8 storage

These rules define the FP8 number itself. They are different from the external quantization scale used later when we map FP16/BF16 tensors into FP8 cache storage.

So E4M3 is a family name unless we specify the exact dtype/standard.

Examples:

  • OCP / ONNX E4M3FN / NVIDIA Transformer Engine E4M3: finite-only E4M3, usually max finite value around ±448.
  • ONNX E4M3FNUZ-style variants: finite-only, no negative zero, different bias, max finite value around ±240.
  • E5M2: larger exponent range, max finite value around ±57344, but only 2 mantissa bits.

For KV cache, E4M3 is commonly used when calibrated quantization scales are available, because it keeps one extra mantissa bit compared with E5M2. That extra precision usually matters more for attention quality than the extra range from E5M2.

For this note, when I explain the bit layout, I am describing generic E4M3/E5M2 ideas. When I mention vLLM/SGLang KV cache behavior, I am describing those backends' documented FP8 KV cache implementation, not redefining the FP8 standard.

Now feel the effect of fewer mantissa bits

Say you have a value 1.0011011 in binary and you need to store it in:

  • FP32 (23 mantissa bits) → stores 00110110000000000000000 → nearly exact
  • FP8 E4M3 (3 mantissa bits) → can only keep 3 mantissa bits, so it must round to the nearest representable FP8 value
original:       1.0011011
nearby FP8s:    1.001 or 1.010
stored result:  whichever is chosen by the rounding rule

This is your quantization error. The value is not just “cut off”; in real implementations it is usually rounded to a nearby representable value, and it may also be saturated/clipped if it exceeds the FP8 range.

What each field actually controls

  • Exponent bits → range
    More exponent bits usually mean a larger exponent window, but the final range also depends on bias and special-value rules.
FP32: exponent = 8 bits → range up to ~3.4 × 10^38
FP8 E4M3FN / OCP / NVIDIA Transformer Engine style → max around ±448
FP8 E4M3FNUZ-style variants → max around ±240
FP8 E5M2 → max around ±57344

If your value exceeds the representable range → overflow / saturation / special value, depending on the exact format and conversion rule.

  • Mantissa bits → precision
    More mantissa bits = more significant digits, finer resolution between two consecutive representable numbers.
FP32:     23 mantissa bits → ~7 decimal digits of precision
FP16:     10 mantissa bits → ~3 decimal digits of precision
FP8 E4M3: 3 mantissa bits  → much coarser precision

If your value falls between two representable numbers → rounding error.

The tricky part: quantization scheme

You can't just naively cast FP16 → FP8. Here we introduce a second, different meaning of “scale”: the external quantization scale.

There are two scales in the full story:

  • internal exponent scale: inside every FP8 value, from 2^(exponent - bias)
  • external quantization scale: metadata used to map FP16/BF16 tensor values into FP8 cache storage

Important

This quantization scale is not a new FP8 standard. The FP8 dtype/standard defines how one 8-bit code maps to one FP8 number. A KV-cache quantization scheme stores FP8 bytes plus scale metadata, and uses that metadata when writing/reading the KV cache.

  • So vLLM/SGLang are not redefining the FP8 bit format by adding scale. They are using a backend FP8 dtype and wrapping it in a KV-cache quantization scheme.
  • Conceptually, scale granularity can be per-tensor, per-channel/head, per-token, or per-block. Finer granularity usually gives better accuracy but adds metadata and implementation overhead.
  • For the current FP8 KV cache implementations discussed in vLLM/SGLang docs, the practical note is stricter: they currently document per-tensor scalar scaling for FP8 KV cache, with finer-grained scaling still a design/development direction rather than the default behavior.

Why this matters for FP8 KV cache

With only 3 mantissa bits, consecutive representable values are far apart. Around 1.x, E4M3 spacing is binary, not decimal-style:

possible E4M3-like normalized values near 1:
1.000, 1.001, 1.010, 1.011, ...

So when you store a K or V vector value in FP8, it gets rounded to a nearby representable value. The external quantization scale tries to stretch the tensor values so that the available FP8 range is used efficiently, reducing both clipping and excessive rounding error.

Where the approximation error shows up

KV cache quantization is lossy. The concern is:

  • K vectors get slightly distorted → attention score distribution shifts
  • V vectors get slightly distorted → the values mixed by attention change
  • Errors accumulate over many layers and long contexts → output quality can degrade

In practice, FP8 E4M3 KV cache often introduces only small accuracy degradation when the backend, scaling factors, and model are suitable.

But this is not automatic:

  • calibrated scales are better than blindly using scale 1.0
  • backend support matters because unfused dequantization can be slow
  • the impact depends on model architecture, sequence length, and quantization format

The tradeoff summary

FP16/BF16 KV FP8 KV
Memory per value 2 bytes 1 byte, plus scale metadata
Cache capacity baseline roughly larger, often close to 2× before overhead
Batch size / concurrency smaller when KV memory is the bottleneck larger when KV memory is the bottleneck
Precision higher-precision baseline lossy quantized approximation
Compute on read none dequantize/rescale on read; some backends may fuse this into attention
  • The main benefit is memory: you can store more cached tokens, support longer contexts, or handle more concurrent requests.
  • The throughput win is strongest when KV memory capacity is the bottleneck and the backend handles dequantization efficiently.
  • If dequantization is not fused with attention, or if the workload is not KV-memory-bound, the speedup may be smaller or even disappear.
