Paper: ReAct: Synergizing Reasoning and Acting in Language Models

Scope: This note focuses on the original ReAct paper: its problem framing, method, experiments, limitations, and infrastructure implications. Later systems such as Toolformer, ReWOO, LATS, vLLM, SGLang, and DistServe are included only for positioning, not as claims about what the original ReAct paper implemented.

Problem

Before ReAct, two relevant directions were usually discussed separately.

  1. Chain-of-Thought (CoT): Question → Reasoning → Answer

    Example:

    • Q: "Roger has 5 apples. He buys 3 more apples. How many apples does he have?"
    • Reasoning: "5 + 3 = 8."
    • Answer: "8 apples."

    The model reasons from its internal knowledge.

    Problem

    • Knowledge may be outdated.
    • The model cannot interact with external tools or environments.
    • Reasoning traces can hallucinate facts and then propagate those errors.

  2. Action / Tool Use: Question → Action → Observation → Action → Answer

    Example:

    • Observation: "You are in the kitchen. You see a cabinet, a sink, and a coffee table."
    • Action: "open cabinet"
    • Observation: "The cabinet contains a mug."
    • Action: "take mug"
    • Answer: "Task complete."

    Problem

    • Action-only agents can interact with an environment.
    • But they do not explicitly reason about high-level goals, subgoals, or recovery.
    • They can repeat bad actions when the observation does not match the plan.

Motivation

The authors' core observation is simple: humans usually do not separate reasoning from acting.

  • We reason to decide what to do next.
  • We act to collect new information.
  • We use the new observation to update the plan.

This motivates ReAct: interleave reasoning traces with actions, so reasoning can guide acting and observations can update reasoning.

Main Contributions

The paper makes four important contributions.

  1. Reasoning and action are combined into one trajectory.

    • The model generates reasoning traces and task-specific actions in an interleaved way.
    • This is different from CoT-only reasoning and action-only tool use.

  2. The action space is augmented with language thoughts.

    • A thought is treated like an internal language action.
    • It does not change the external environment, but it updates the model's context for future reasoning and acting.

  3. ReAct works across different task types.

    • Knowledge-intensive reasoning: HotpotQA and FEVER.
    • Interactive decision making: ALFWorld and WebShop.
    • The high-level idea stays the same, but the prompt format and action space are task-specific.

  4. The trajectory is interpretable.

    • Humans can inspect what came from internal reasoning and what came from external observations.
    • This makes failures easier to diagnose than plain answer generation.

Method

ReAct Prompt Structure

ReAct uses three kinds of tokens.

  1. Thought: internal reasoning.
    • Example: Thought: "I need more information."
  2. Action: command sent to a tool or environment.
    • Example: Action: "Search[Eiffel Tower]"
  3. Observation: result returned by the tool or environment.
    • Example: Observation: "The Eiffel Tower is in Paris."

The basic loop is: Thought → Action → Observation → Thought → Action → Observation.

Important nuance

Original ReAct is an observation-dependent trajectory method. The next step is conditioned on the accumulated thoughts, actions, and observations. It is not a parallel tree-search algorithm.

Dense vs Sparse Thoughts

This difference comes from the prompt design, not from a separately trained task-type classifier.

  1. Model setup

    • The paper mainly uses a frozen PaLM-540B model with few-shot ReAct examples.
    • The examples show the model what kinds of outputs are allowed: Thought, Action, and Observation.
    • So the model's behavior is induced by in-context trajectories, not by a new MoE routing mechanism.

  2. Knowledge tasks: HotpotQA and FEVER

    • The authors use prompts where reasoning traces and actions alternate densely.
    • The model is shown a pattern like: Thought → Action → Observation → Thought → Action → Observation.
    • This makes sense because these tasks require repeated evidence lookup and fact checking.

  3. Decision-making tasks: ALFWorld and WebShop

    • The authors write prompts with sparse reasoning traces.
    • The prompt still gives the model the option to output thoughts, but it does not require a thought before every action.
    • The model then decides when to output a thought versus an action within that prompted format.

    Precision point

    In the ReAct paper, sparse thinking is a prompting strategy. It is not evidence that the model was trained to autonomously classify task types and choose a reasoning density from scratch.

Action Spaces

The action space changes by benchmark.

  1. HotpotQA / FEVER
    • Search[entity]: retrieve information from a Wikipedia page or similar entities.
    • Lookup[string]: find the next sentence containing a string.
    • Finish[answer]: return the final answer.
  2. ALFWorld
    • Text actions in a simulated household, such as going to a location, opening an object, taking an item, or placing an item.
  3. WebShop
    • Web navigation actions such as searching, choosing products, selecting options, and submitting the final product choice.

Paper Trajectory Example

A real HotpotQA-style ReAct trajectory in the paper works like this:

  • The question asks which device, besides the Apple Remote, can control the program the Apple Remote was originally designed for.
  • The model first searches for the Apple Remote.
  • The observation points it toward Front Row.
  • The model searches for Front Row, then reformulates the search when the first result is not useful.
  • The later observation identifies keyboard function keys as another control method.
  • The model finishes with that answer.

The important part is not the specific entity. The important part is the feedback loop: search result → updated thought → better search → final answer.

Experimental Setup

The paper evaluates ReAct on four benchmarks.

  1. HotpotQA
    • Multi-hop question answering.
    • The model must retrieve and combine information from multiple Wikipedia facts.
  2. FEVER
    • Fact verification.
    • The model predicts whether a claim is supported, refuted, or lacks enough information.
  3. ALFWorld
    • Text-based household environment.
    • The model must complete tasks over long action horizons with sparse rewards.
  4. WebShop
    • Web shopping environment.
    • The model must navigate product pages and choose an item satisfying a user instruction.

The main model in the paper is PaLM-540B under few-shot prompting. The authors also run fine-tuning experiments on smaller PaLM models using generated trajectories.

Key Results

The paper's results are more nuanced than "ReAct always beats CoT."

Task Result Takeaway
HotpotQA ReAct beats Act-only, but is slightly below CoT in the basic prompting setup. ReAct + CoT-SC performs best. ReAct grounds reasoning with retrieval, but CoT can still be strong when reasoning structure matters.
FEVER ReAct beats both Act-only and CoT; CoT-SC → ReAct performs best. External evidence is especially useful for fact verification.
ALFWorld ReAct improves success rate by about 34% absolute over the compared imitation/RL baseline. Sparse reasoning helps long-horizon environment interaction.
WebShop ReAct improves success rate by about 10% absolute over the compared baseline. Reasoning helps navigate noisy real-world text environments.

Result takeaway

ReAct's value is not just higher accuracy. Its bigger contribution is showing that reasoning traces and environment actions can improve each other inside the same task-solving trajectory.

Limitations

This section matters for both paper reading and infrastructure design.

  1. Sequential, observation-dependent execution
    • In the original ReAct paper, the agent follows a trajectory.
    • The next thought/action depends on the current context and the latest observation.
    • This makes ReAct easy to inspect, but it also creates waiting points.
  2. Tool latency
    • Suppose one LLM call takes 300 ms and one search call takes 500 ms.
    • Five ReAct rounds cost roughly 5 × (300 + 500) = 4 seconds.
    • This number is illustrative, but the pattern is real: repeated tool calls add latency.
  3. Context growth
    • Every round appends new Thought, Action, and Observation text into the prompt.
    • Longer trajectories mean longer prompts, higher KV cache usage, and more memory pressure.
  4. Many inference calls
    • A classic chatbot may turn one user request into one long generation.
    • ReAct can turn one user request into several short generations.
    • This makes the same user task more expensive and harder to schedule.
  5. Reasoning rigidity
    • The paper finds that interleaving thoughts, actions, and observations improves grounding.
    • But the structure can also reduce flexibility compared with free-form CoT.
    • One failure mode is repeating previous thoughts or actions instead of recovering.
  6. Search / observation failure
    • ReAct depends heavily on whether the tool returns useful information.
    • A bad search result can derail the next reasoning step.
    • The model may need to reformulate the search, but it does not always recover.

Key limitation

ReAct reduces hallucination by grounding reasoning in observations, but it pays for that grounding with sequential waiting, prompt growth, and dependence on tool quality.

Infrastructure Implications

ReAct made a now-common agent workload pattern concrete.

  • Traditional serving: User → one long generation.
  • Agent serving: User → short generation → tool call → short generation → tool call → answer.

The workload becomes:

  • bursty: many short model calls instead of one continuous generation.
  • asynchronous: tool calls return at different times.
  • latency-sensitive: each next reasoning/action step often waits for the previous observation.
  • stateful: every step depends on the accumulated trajectory.
  • cache-heavy: repeated calls reuse a growing prefix, so KV cache management matters.

Infrastructure takeaway

Agent serving is not just longer prompting. It is repeated, stateful, tool-linked inference over a growing trajectory.

Later systems should be described carefully. They address related pressure points, but they are not all direct descendants of ReAct.

  1. vLLM / PagedAttention
    • Related pressure point: KV cache memory pressure and fragmentation.
    • Main idea: manage KV cache efficiently with paged memory blocks.
  2. SGLang
    • Related pressure point: structured LLM programs, agent control, RAG, and multi-call execution.
    • Main idea: expose program structure to the runtime so it can optimize execution.
  3. DistServe
    • Related pressure point: prefill and decode have different bottlenecks and latency goals.
    • Main idea: disaggregate prefill and decode resources.
  4. ReWOO
    • Related pressure point: ReAct-style observation-dependent reasoning repeatedly halts for tool responses and re-sends growing prompts.
    • Main idea: plan first, gather evidence with workers, then solve with the collected evidence.
  5. LATS
    • Related pressure point: ReAct follows one trajectory and does not search over multiple possible reasoning/action paths.
    • Main idea: expand ReAct-style steps into Monte Carlo tree search.

Comparison With Nearby Methods

Method Core idea Tool / environment use Execution shape Main limitation
CoT Generate reasoning before the answer. No external tool by default. One reasoning chain. Can hallucinate unsupported facts.
Act-only Generate actions from observations. Yes. Observation → Action trajectory. Lacks explicit high-level reasoning.
ReAct Interleave thoughts, actions, and observations. Yes. Sequential observation-dependent trajectory. Latency, context growth, tool-result dependence.
Toolformer Train a model to decide when and how to call APIs. Yes, through learned API calls. API calls inserted into language modeling. Requires tool-use data construction and filtering.
ReWOO Plan first, execute tool calls, then solve. Yes. Plan → Work → Solve. Plan can be wrong before evidence arrives.
LATS Use tree search over reasoning/action steps. Yes. Search tree over possible trajectories. More expensive than a single trajectory.

Summary

  1. ReAct = Reason + Act.
  2. The core loop is Thought → Action → Observation.
  3. Original ReAct is a sequential, observation-dependent trajectory method, not a tree-search method.
  4. ReAct reduces hallucination by grounding reasoning in tool/environment observations.
  5. Modern agent-serving research studies the pressure points ReAct makes visible: repeated calls, tool latency, context growth, KV cache pressure, scheduling, and execution structure.
