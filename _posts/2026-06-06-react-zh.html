论文： ReAct: Synergizing Reasoning and Acting in Language Models

范围： 这篇笔记聚焦原始 ReAct 论文：问题背景、方法、实验、局限性，以及对基础设施的影响。Toolformer、ReWOO、LATS、vLLM、SGLang、DistServe 等后续系统只用于定位和对比，不表示原始 ReAct 论文实现了这些系统。

问题

在 ReAct 之前，两类相关方向通常是分开讨论的。

  1. Chain-of-Thought (CoT)： Question → Reasoning → Answer

    示例：

    • Q： "Roger has 5 apples. He buys 3 more apples. How many apples does he have?"
    • Reasoning： "5 + 3 = 8."
    • Answer： "8 apples."

    模型基于自己的内部知识进行推理。

    问题

    • 知识可能已经过时。
    • 模型不能和外部工具或环境交互。
    • reasoning traces 可能会幻觉事实，并把错误继续传播下去。

  2. Action / Tool Use： Question → Action → Observation → Action → Answer

    示例：

    • Observation: "You are in the kitchen. You see a cabinet, a sink, and a coffee table."
    • Action: "open cabinet"
    • Observation: "The cabinet contains a mug."
    • Action: "take mug"
    • Answer: "Task complete."

    问题

    • Action-only agents 可以和环境交互。
    • 但它们不会显式地推理高层目标、子目标或失败恢复。
    • 当 observation 和计划不匹配时，它们可能会重复错误 actions。

动机

作者的核心观察很简单：人类通常不会把 reasoning 和 acting 完全分开。

  • 我们通过 reasoning 判断下一步该做什么。
  • 我们通过 acting 收集新信息。
  • 我们利用新的 observation 更新计划。

这就引出了 ReAct：把 reasoning traces 和 actions 交错起来，让 reasoning 指导 acting，也让 observations 更新 reasoning。

主要贡献

这篇论文有四个重要贡献。

  1. Reasoning 和 action 被组合到同一条 trajectory 中。

    • 模型以交错方式生成 reasoning traces 和 task-specific actions。
    • 这不同于只做 CoT reasoning，也不同于只做 action 的 tool use。

  2. Action space 被扩展，加入了 language thoughts。

    • thought 被当作一种内部 language action。
    • 它不会改变外部环境，但会更新模型上下文，影响之后的 reasoning 和 acting。

  3. ReAct 可以用于不同类型的任务。

    • Knowledge-intensive reasoning：HotpotQA 和 FEVER。
    • Interactive decision making：ALFWorld 和 WebShop。
    • 高层思路保持一致，但 prompt format 和 action space 是 task-specific 的。

  4. Trajectory 是可解释的。

    • 人可以检查哪些内容来自内部 reasoning，哪些内容来自外部 observations。
    • 这比直接生成答案更容易诊断失败原因。

方法

ReAct Prompt Structure

ReAct 使用三类 token。

  1. Thought：内部 reasoning。
    • Example: Thought: "I need more information."
  2. Action：发送给工具或环境的命令。
    • Example: Action: "Search[Eiffel Tower]"
  3. Observation：工具或环境返回的结果。
    • Example: Observation: "The Eiffel Tower is in Paris."

基本循环是：Thought → Action → Observation → Thought → Action → Observation。

重要细节

原始 ReAct 是 observation-dependent trajectory 方法。下一步会基于已经累积的 thoughts、actions 和 observations。它不是并行 tree-search 算法。

Dense vs Sparse Thoughts

这种差异来自 prompt design，不是来自一个单独训练出来的 task-type classifier。

  1. 模型设置

    • 论文主要使用 frozen PaLM-540B，并配合 few-shot ReAct examples。
    • 这些 examples 告诉模型允许输出哪些类型：Thought、Action 和 Observation。
    • 所以模型行为是由 in-context trajectories 诱导出来的，而不是由新的 MoE routing mechanism 产生的。

  2. Knowledge tasks：HotpotQA 和 FEVER

    • 作者使用的 prompts 中，reasoning traces 和 actions 会比较密集地交替出现。
    • 模型看到的模式类似：Thought → Action → Observation → Thought → Action → Observation。
    • 这很合理，因为这些任务需要反复查找证据并进行事实核查。

  3. Decision-making tasks：ALFWorld 和 WebShop

    • 作者写的是 sparse reasoning traces 的 prompts。
    • prompt 仍然允许模型输出 thoughts，但不要求每个 action 前都必须有 thought。
    • 模型会在这个 prompted format 内决定什么时候输出 thought，什么时候输出 action。

    精确表述

    在 ReAct 论文中，sparse thinking 是一种 prompting strategy。它不能证明模型从零开始被训练出了自动判断任务类型并选择 reasoning density 的能力。

Action Spaces

Action space 会随 benchmark 改变。

  1. HotpotQA / FEVER
    • Search[entity]：从 Wikipedia 页面或相似实体中检索信息。
    • Lookup[string]：寻找下一句包含某个字符串的句子。
    • Finish[answer]：返回最终答案。
  2. ALFWorld
    • 文本形式的模拟家庭环境 actions，例如去某个位置、打开物体、拿起物品，或放置物品。
  3. WebShop
    • 网页导航 actions，例如搜索、选择商品、选择选项，以及提交最终商品选择。

Paper Trajectory Example

论文中的一个 HotpotQA-style ReAct trajectory 大致是这样工作的：

  • 问题询问：除了 Apple Remote 之外，哪个设备也可以控制 Apple Remote 最初设计用于控制的程序。
  • 模型先搜索 Apple Remote。
  • observation 把它指向 Front Row。
  • 模型搜索 Front Row；当第一个结果不够有用时，它会重新组织搜索。
  • 后续 observation 指出键盘 function keys 是另一种控制方式。
  • 模型用这个答案结束。

重要的不是这个具体实体，而是反馈循环：search result → updated thought → better search → final answer。

实验设置

论文在四个 benchmarks 上评估 ReAct。

  1. HotpotQA
    • Multi-hop question answering。
    • 模型需要从多个 Wikipedia facts 中检索并组合信息。
  2. FEVER
    • Fact verification。
    • 模型需要判断一个 claim 是 supported、refuted，还是没有足够信息。
  3. ALFWorld
    • Text-based household environment。
    • 模型需要在 long action horizon 和 sparse rewards 下完成任务。
  4. WebShop
    • Web shopping environment。
    • 模型需要浏览商品页面，并选择满足用户指令的商品。

论文中的主模型是 PaLM-540B，使用 few-shot prompting。作者也用生成出来的 trajectories 对较小的 PaLM models 做了 fine-tuning experiments。

关键结果

论文结果比 “ReAct 总是胜过 CoT” 更微妙。

任务 结果 结论
HotpotQA ReAct 胜过 Act-only，但在 basic prompting setup 中略低于 CoT。ReAct + CoT-SC 表现最好。 ReAct 用 retrieval 来 grounding reasoning，但当 reasoning structure 很重要时，CoT 仍然很强。
FEVER ReAct 胜过 Act-only 和 CoT；CoT-SC → ReAct 表现最好。 外部证据对 fact verification 尤其有用。
ALFWorld 相对于论文比较的 imitation/RL baseline，ReAct 的 success rate 绝对提升约 34%。 Sparse reasoning 有助于 long-horizon environment interaction。
WebShop 相对于论文比较的 baseline，ReAct 的 success rate 绝对提升约 10%。 Reasoning 有助于在嘈杂的真实文本环境中导航。

结果结论

ReAct 的价值不只是更高准确率。它更大的贡献是证明：reasoning traces 和 environment actions 可以在同一条 task-solving trajectory 中互相增强。

局限性

这一节对论文阅读和 infrastructure design 都很重要。

  1. Sequential, observation-dependent execution
    • 在原始 ReAct 论文中，agent 遵循一条 trajectory。
    • 下一步 thought/action 依赖当前上下文和最新 observation。
    • 这让 ReAct 容易检查，但也产生了等待点。
  2. Tool latency
    • 假设一次 LLM call 需要 300 ms，一次 search call 需要 500 ms。
    • 五轮 ReAct 大约需要 5 × (300 + 500) = 4 seconds。
    • 这个数字只是说明性例子，但模式是真实的：重复 tool calls 会增加 latency。
  3. Context growth
    • 每一轮都会把新的 Thought、Action 和 Observation 文本追加进 prompt。
    • 更长的 trajectories 意味着更长 prompts、更高 KV cache usage，以及更大的 memory pressure。
  4. Many inference calls
    • 经典 chatbot 可能把一个用户请求变成一次长 generation。
    • ReAct 可能把一个用户请求变成多次短 generation。
    • 这会让同一个用户任务更贵，也更难调度。
  5. Reasoning rigidity
    • 论文发现，交错 thoughts、actions 和 observations 可以提升 grounding。
    • 但这个结构也可能比 free-form CoT 更不灵活。
    • 一种失败模式是重复之前的 thoughts 或 actions，而不是恢复。
  6. Search / observation failure
    • ReAct 很依赖工具是否返回有用信息。
    • 不好的 search result 可能会带偏下一步 reasoning。
    • 模型可能需要重新组织 search，但不一定总能恢复。

核心局限

ReAct 通过 observations 来 grounding reasoning，从而减少 hallucination；但这种 grounding 的代价是 sequential waiting、prompt growth，以及对 tool quality 的依赖。

基础设施影响

ReAct 把一种现在很常见的 agent workload pattern 具体化了。

  • Traditional serving： User → one long generation。
  • Agent serving： User → short generation → tool call → short generation → tool call → answer。

这种 workload 会变成：

  • bursty：很多次短 model calls，而不是一次连续 generation。
  • asynchronous：tool calls 会在不同时间返回。
  • latency-sensitive：下一步 reasoning/action 通常要等待前一个 observation。
  • stateful：每一步都依赖累积起来的 trajectory。
  • cache-heavy：重复 calls 会复用不断增长的 prefix，因此 KV cache management 很重要。

Infrastructure takeaway

Agent serving 不只是更长的 prompting。它是在不断增长的 trajectory 上进行 repeated、stateful、tool-linked inference。

后续系统需要谨慎描述。它们解决相关 pressure points，但并不全是 ReAct 的直接后代。

  1. vLLM / PagedAttention
    • 相关 pressure point：KV cache memory pressure 和 fragmentation。
    • 核心思路：用 paged memory blocks 高效管理 KV cache。
  2. SGLang
    • 相关 pressure point：structured LLM programs、agent control、RAG，以及 multi-call execution。
    • 核心思路：把 program structure 暴露给 runtime，让 runtime 优化执行。
  3. DistServe
    • 相关 pressure point：prefill 和 decode 有不同瓶颈和 latency goals。
    • 核心思路：disaggregate prefill and decode resources。
  4. ReWOO
    • 相关 pressure point：ReAct-style observation-dependent reasoning 会反复因为 tool responses 停下来，并重新发送增长中的 prompts。
    • 核心思路：先 plan，再用 workers 收集 evidence，最后用收集到的 evidence solve。
  5. LATS
    • 相关 pressure point：ReAct 只跟随一条 trajectory，不会搜索多条可能的 reasoning/action paths。
    • 核心思路：把 ReAct-style steps 扩展成 Monte Carlo tree search。

与邻近方法对比

方法 核心思路 Tool / environment use Execution shape 主要局限
CoT 先生成 reasoning，再给出答案。 默认没有外部工具。 一条 reasoning chain。 可能 hallucinate unsupported facts。
Act-only 基于 observations 生成 actions。 有。 Observation → Action trajectory。 缺少显式的 high-level reasoning。

Toolformer 训练模型判断何时以及如何调用 APIs。 有，通过 learned API calls。 API calls 被插入 language modeling。 需要构造和过滤 tool-use data。

总结

  1. ReAct = Reason + Act。
  2. 核心循环是 Thought → Action → Observation。
  3. 原始 ReAct 是一种 sequential, observation-dependent trajectory method，不是 tree-search method。
  4. ReAct 通过 tool/environment observations 来 grounding reasoning，从而减少 hallucination。
  5. 现代 agent-serving research 会研究 ReAct 暴露出的 pressure points：repeated calls、tool latency、context growth、KV cache pressure、scheduling 和 execution structure。
